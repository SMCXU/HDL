# 《钢铁突围》完整打磨与验收规划

版本：1.0  
制定日期：2026-11-03（Asia/Shanghai）  
项目定位：Android 离线单机横版射击游戏  
当前阶段：0.1.0 可玩原型，已接入第二轮位图美术样板  
执行依据：用户已授权按计划自主开发，常规实现无需逐项确认；设备条件、系统权限和正式签名条件不足时再请求协助。

## 1. 目标与完成定义

以已批准的“暗夜重工业 × 科幻突击队”概念图为视觉目标，将现有原型打磨成动作准确、战斗反馈清晰、关卡节奏完整，并经过真实 Android 设备验证的阶段交付版本。

本规划同时覆盖玩法、工程、美术、特效、音频、操作、性能和交付。视觉目标是接近参考图的材质、比例、层次与氛围；不承诺动态游戏与单张概念图逐像素一致，不以铺设概念截图代替可交互场景。

完成必须同时满足：

- 一关从开始、三段推进、检查点、Boss 到结算完整可玩，失败与重试稳定。
- 主角基本动作齐备，朝向、瞄准、枪口、弹道、碰撞关系准确。
- 三类敌人和 Boss 有清晰预警与反馈，不用不可辨认的伤害制造难度。
- 美术、HUD、特效、声音风格统一，关键游戏信息在手机上清楚可辨。
- 原创资产源文件、生成记录、依赖许可、构建步骤与验收证据齐全。
- 通过本文件第 11 节的最终验收；未通过前持续标为原型或阶段版本。

## 2. 固定边界

| 类别 | 约束 |
| --- | --- |
| 技术 | Godot 4.7.2、GDScript、Android Compatibility 渲染 |
| 模式 | 离线单机，无联网、账户、广告和内购 |
| 内容 | 一名主角、一关、三类敌人、一个 Boss、两种武器 |

不新增武器种类、敌人种类、关卡、技能树或成长系统。性能不足时优先调整装饰与特效，不改变已确认的核心玩法范围。

## 4. 总体执行策略

按“建立基线—动作样板—战斗完善—场景与声音—整关调优—完整验收”执行。每轮均保持游戏可运行；不一次性替换全部系统后再验收。

第一段外围防线作为样板段，覆盖平地射击、跳跃平台、两种武器与三类敌人。其动作、材质和反馈通过检查后再推广到整关。Boss 单独安排固定状态检查与实际战斗检查。

工程拆分随功能进行，不做脱离需求的大规模重写。逻辑状态控制玩法，动画仅表现状态；动画播放失败不得阻塞伤害、死亡或结算。

### 4.1 阶段总览

以下均为待执行任务。人日为排期参考，不是承诺工期；资产返工、真机问题和反馈轮次会影响耗时，各阶段需在完成门槛满足后推进。

| 阶段 | 主要交付 | 依赖 | 参考投入 | 完成门槛 |
| --- | --- | --- | --- | --- |
| M0 基线与规范 | 可复现基线、性能采样方案、资产标准 | 当前原型 | 1～2 人日 | 基线可启动，证据和设备信息齐全 |
| M1 主角与操作样板 | 完整基础动作、枪口同步、触屏修正 | M0 | 4～7 人日 | 动作切换、瞄准和多指实际检查通过 |
| M2 敌人与战斗演出 | 三类敌人、两种武器特效、Boss 演出 | M1 | 5～8 人日 | 两种 Boss 攻击可预判，反馈与命中一致 |
| M3 场景、HUD 与音频 | 三段环境、独立视差、完整 HUD、混音 | M1；反馈音效跟随 M2 | 5～8 人日 | 整关视觉统一、无明显接缝、循环听检通过 |
| M4 关卡与稳定性 | 遭遇配置、节奏调优、性能优化 | M2、M3 | 3～5 人日 | 真人计时与当前设备持续性能达标 |
| M5 完整验收与交付 | 测试矩阵、修复、APK、源码和说明 | M4 | 3～5 人日 | 第 11 节检查项全部满足 |

合计参考约 21～35 人日，包含实现与常规验证，不包含等待额外设备、正式签名条件和大规模方向变更。先完成 M0、M1，再按实测结果更新剩余估算。当前文档没有设置日历截止日期。

### 4.2 每轮工作闭环

1. 记录本轮目标和对应任务 ID，保留修改前的可复现基线。
2. 制作资产、接入逻辑与表现、更新资产清单。
3. 修改玩法后执行 `python3 tools/manage.py test`；仅为重要新行为补测试。
4. 修改 UI/渲染后查看实际引擎截图；动画需查看连续录像或实际运行。
5. 构建 Android 调试 APK，安装到当前设备，记录本轮实际检查范围。
6. 更新测试报告与已知问题，保留截图、录像摘要和性能数据。
7. 未满足完成门槛则修复；资源或设备不足的检查项明确标为未测试。

## 5. 详细工作包

### M0：基线、工程边界与制作规范

| ID | 工作 | 产出与验收 |
| --- | --- | --- |
| BASE-01 | 记录引擎、APK、源码快照与设备信息 | 版本可追溯，APK 与对应源码可对应；不将 work/ 密钥纳入快照 |
| BASE-02 | 固定外围、密集交火、Boss 三组检查位置 | 可复现的桌面检查状态与真实游玩路线分开保存 |
| BASE-03 | 建立调试指标面板/采样输出 | FPS、帧耗时、对象数、弹丸数、特效数、音效占用和内存有时间戳；发布默认关闭 |
| BASE-04 | 明确模块职责和资产锚点 | 渲染无玩法权威；动画、物理、输入使用统一角色坐标和枪口定义 |
| BASE-05 | 当前手机真实游玩初次采样 | 保存优化前数据，不能以桌面或逻辑模拟代替 |

建议逐步形成角色控制、角色表现、武器、敌人、Boss、遭遇流程、场景层、HUD 和特效管理等职责。保留现有输入与音频模块，避免为了重构改变操作手感。

### M1：主角动作与输入准确性

#### 5.1 动作资产

以下帧数为制作起点，可按实际播放调整；不能仅凭达到帧数判断完成。

| 动作 | 建议内容 | 主要验收点 |
| --- | --- | --- |
| 待机 | 4～6 帧，轻微呼吸和持枪重心 | 循环无跳变，无明显漂移 |
| 跑动 | 6～8 帧，下半身完整迈步 | 脚底锚点固定，左右朝向比例一致 |
| 起跳/下落 | 蹬地、上升、顶点、下落各阶段姿态 | 重复切换无抖动；与实际速度阶段一致 |
| 落地 | 2～3 帧缓冲与轻量尘雾 | 不引入强制操作硬直 |
| 下蹲/起身 | 进入、蹲姿、蹲姿移动、退出 | 枪口高度与受击框同步 |
| 受击 | 2～3 帧短暂姿态和护甲反馈 | 不连扣生命，无敌状态可辨认 |
| 死亡 | 5～8 帧倒地与结束姿态 | 不再接受攻击输入；重试完整恢复 |
| 持枪 | 水平、斜上、垂直三个方向 | 上下半身组合自然，瞄准方向准确 |

优先拆分上半身持枪与下半身移动；如现有图集不适合拆分，补制成套帧并对齐锚点。不能靠拉伸、旋转整个人物代替正上方持枪。

#### 5.2 行为与操作任务

| ID | 工作 | 验收 |
| --- | --- | --- |
| ACT-01 | 建立移动/空中/下蹲/受击/死亡状态与瞄准组合 | 快速跑跳、转身、射击无状态卡死；保留跳跃缓冲和离台宽限 |
| ACT-02 | 所有朝向使用统一枪口锚点 | 左右平射、斜上、正上、蹲射逐项检查；弹丸从枪口发出 |
| ACT-03 | 处理开火、落地、受击的表现优先级 | 表现不吞输入，死亡不能被普通动作覆盖 |
| INPUT-01 | 校准触屏按钮显示、点击区域和缩放 | 所有设置范围内按钮可见可按，方向区不产生意外重叠 |
| INPUT-02 | 三指移动＋跳跃＋射击及滑出按钮释放 | 连续至少 5 分钟实操，无粘键、无意外连续跳跃 |
| INPUT-03 | 手柄与暂停/恢复检查 | 蓝牙手柄实测；未获得手柄则标为未测试 |

M1 交付：外围动作样板 APK、动作检查录像、方向/枪口对照图、输入检查记录。不能仅以静态姿势截图完成动作验收。

### M2：敌人、武器、特效与 Boss

#### 5.3 敌人表现

| 类型 | 需要补齐的表现 | 验收重点 |
| --- | --- | --- |
| 步兵 | 巡逻、发现、举枪、开火、受击、倒地 | 朝向与攻击一致，发现/开火有可见提示 |
| 炮台 | 炮口转向或明确射向、蓄力灯、后坐、冒烟、爆炸 | 炮口与发弹点一致，发射前能辨认危险 |
| 无人机 | 悬浮、移动倾斜、推进器、攻击预警、失控击毁 | 图形位置与命中框一致，不出现长时间脱离轮廓的受击区域 |

敌人预警先以 0.25～0.45 秒作为调试起点，再通过实际躲避体验调整。预警时长、弹速和玩家反应空间一起评估，不单独提高敌方弹速凑难度。

#### 5.4 战斗特效任务

| ID | 内容 | 控制原则 |
| --- | --- | --- |
| FX-01 | 步枪、散弹分别制作枪火、后坐和弹壳 | 明显区分两种武器，枪火不持续遮住前方敌人 |
| FX-02 | 弹道、敌方危险弹丸、命中火星、装甲碎片 | 敌我颜色和轮廓有双重区分，不只依赖颜色 |
| FX-03 | 击毁火焰、扩散碎片、余烟分阶段播放 | 近景爆炸不掩盖危险弹丸和落脚点 |
| FX-04 | 轻量震动、可选重击短顿帧 | 默认克制；不靠持续震屏制造冲击，不能破坏物理时序 |
| FX-05 | 降低闪光/震动设置及效果数量预算 | 设置即时生效并保存；超限优先丢弃远处装饰效果 |
| FX-06 | 暂停、重试、结算的效果清理 | 不残留上轮爆炸、闪白、震动或弹壳 |

先建立少量精制效果再扩充，优先使用特效图集与复用机制。效果播放完成必须释放或回收，不在开火时反复创建无上限节点。

#### 5.5 Boss 专项

| ID | 工作 | 验收 |
| --- | --- | --- |
| BOSS-01 | 机械门、警灯、入场音效和 Boss 激活联动 | 只触发一次；演出期间伤害规则明确，不出现无提示受伤 |
| BOSS-02 | 扇形与瞄准射击采用不同预警 | 两种模式从画面即可区分；枪口、弹道和命中一致 |
| BOSS-03 | 低血量破损、烟雾、电弧和攻击节奏切换 | 阶段切换无重复伤害和异常补弹 |
| BOSS-04 | 局部爆炸、核心破裂、余烟与胜利结算 | 玩家击败后不再受伤；计分、结算和保存只执行一次 |
| BOSS-05 | 死亡后重试、检查点进入与暂停恢复 | 无旧弹丸、旧动画、旧音效或错误阶段残留 |

M2 交付：战斗特效 APK、敌人/Boss 完整行为录像、密集交火检查、对应行为回归结果。

### M3：场景、HUD 与音频统一

#### 5.6 场景制作

| 层级 | 制作内容 | 建议滚动关系 |
| --- | --- | --- |
| 天空/最远景 | 月亮、云、极远厂区 | 相机速度的 0～0.15 倍 |
| 远景 | 工厂轮廓、烟囱、远处灯光 | 0.15～0.30 倍 |
| 中景 | 厂房、管线、巡逻探照灯 | 0.35～0.65 倍 |
| 玩法层 | 实际地面、可踩平台、拾取物、角色 | 与世界坐标一致 |
| 少量前景 | 支架、线缆、薄烟 | 可略快于相机，禁止遮挡关键交火 |

滚动比例为美术调试起点，不作为必须全部使用的层数。层数应服从可读性与设备预算。

三段关卡分别表现为：外围防线的冷蓝夜色、装配车间的机械光与蒸汽、核心入口的红色警报与能源结构。场景变化与实际推进同步，不新增关卡数量。

任务 ENV-01～ENV-04：分层重制、循环接缝修复、三段过渡、可踩平台视觉规范。验收时连续横向移动至少两个背景循环，检查露底、接缝、突然重复和错误遮挡；全部可踩边缘与碰撞平面对齐，装饰平台不误导玩家。

#### 5.7 HUD 与触屏

任务 UI-01～UI-04：武器与状态图标、生命与 Boss 血条、操作按钮与反馈、暂停/设置/失败/通关界面统一。

- 内容优先级：玩家/危险弹丸/落脚点 ＞ 操作按钮与生命 ＞ 环境装饰。
- 支持按钮大小和透明度设置，显示区域与实际触摸区域一起校准。
- 横屏长宽比至少检查 16:9、约 19.5:9、20:9；模拟与真机分开记录。
- 当前以保持玩法画幅和安全区为优先，宽屏是否保留侧边留白按实际体验决定，不拉伸角色。
- Android 返回键、刘海/挖孔、手势区与暂停入口不冲突。
- 移动端界面显示触屏操作提示，不仅显示键盘说明。

#### 5.8 音频

任务 AUD-01～AUD-05：武器差异化、材质命中差异、预警与 Boss 演出同步、混音优先级、循环与过渡。

- 保留原创确定性合成源文件；需要新音色时扩展源工程，不引入无来源采样。
- 警告声、受击和关键状态音优先于重复枪声；相同音效限制密集叠加。
- 在手机外放和耳机分别听检，不能用编辑器波形检查代替听检。
- 关卡与 Boss 音乐各连续听至少 3 次循环，无明显断点、爆音或音量跳变。
- 密集战斗至少听检 5 分钟；射击不淹没预警，长时间不出现明显刺耳失真。
- 切后台、暂停、恢复、重试时无遗留声音和重复音乐。

M3 交付：全关视听 APK、三段对比截图、连续推进录像、外放/耳机听检表。

### M4：关卡节奏、工程与性能

#### 5.9 关卡体验

任务 LEVEL-01～LEVEL-04：三段遭遇组织、跳跃与瞄准挑战、检查点/Boss 难度、真人通关计时。

目标是熟悉基础操作后的正常完整成功通关约 3～5 分钟，不包含暂停、死亡重试和刻意停留。至少记录 3 次有效成功通关，报告每次时长和中位数；少量样本不能宣称适用于全部玩家。

若偏短，调整遭遇组合、路径利用和战斗节奏；若偏长，排查敌人耐久、重复流程和不必要等待。禁止用强制等待、空跑或单纯堆血量凑时长。另记录初次试玩的死亡位置与误操作，避免熟练开发者体验掩盖难点。

#### 5.10 工程深化

任务 ENG-01～ENG-04：按职责拆分角色/敌人/Boss/关卡流程，将敌人和遭遇配置移入 Resource，统一动画事件接口，完善生命周期清理。

重构逐项进行，移动与命中规则需保持回归；不在同一轮同时重写全部控制、碰撞和表现系统。若变更行为，记录具体前后差异。

## 7. 性能预算与优化方案

### 7.1 目标与统计口径

下列数值为待实测校准的工程目标，不是当前成绩。M0 采样后冻结当前手机的验收预算，并记录调整原因。不得测试失败后仅靠放宽指标宣称通过。

| 指标 | 当前设备 60 FPS 档初始目标 | 测量要求 |
| --- | --- | --- |
| 帧率/帧耗时 | 目标 60 FPS；帧耗时中位数不高于 16.7ms、P95 不高于 20ms、P99 不高于 33.3ms | 排除加载与主动暂停段并明确排除范围；同时报告慢帧，不能只报平均值 |
| 明显卡顿 | 游戏战斗段无可稳定复现的 ≥100ms 帧 | 记录次数、位置与触发原因；系统外部干扰单独标记 |
| 长时趋势 | 20 分钟内不出现持续降帧、崩溃、ANR 或随时间恶化的卡顿 | 比较前 5 分钟与末 5 分钟，报告温度、充电状态和采样方法 |
| 内存 | 资源稳定加载后，重复重试不单调增长 | 初始目标：20 次重试后稳定点增量不超过基线 10% 或 20MiB 中较大者；区分资源缓存与泄漏 |
| 启动 | 冷启动到可操作菜单初始目标 ≤5 秒 | 连测 3 次，记录设备与方法；启动器返回时间仅为参考 |
| 反馈 | 输入后下一物理步响应，明显视觉反馈目标 ≤100ms | 实际触屏录像抽样；不能将程序收到事件的时间当作完整触屏延迟 |

若低端设备无法稳定运行 60 FPS，制定单独的 30 FPS 档：帧耗时目标按约 33.3ms 设计，玩法仍维持固定物理步长。低端档需单独实测和标注，不能与 60 FPS 档混报。

Android 系统内存、Godot 进程指标和纹理显存估计须分别注明；不能将单一监视值当作全部 GPU 内存。温度若只能读取电池传感器，也不能说成 SoC 核心温度。

### 7.2 首轮资源预算

- 保留目前 12 路音效上限，先增加优先级与替换策略，不盲目增加声道。
- 保留装饰事件队列当前 64 个上限作为起点；另统计实际子粒子、烟雾面积和绘制量。
- 弹丸与敌人按正常玩法峰值设预算，禁止为了优化静默吞掉必要危险弹丸。
- 纹理解码内存按尺寸×格式估算；PNG 文件体积不能代替运行内存估算。
- 初期建议将常驻图集与背景纹理总量控制在约 64MiB 的未压缩 RGBA 等效预算内，再依据设备采样调整。

### 7.3 优化顺序

1. 测量 CPU、绘制、透明叠加、资源加载和音频占用，找到主要瓶颈。
2. 去除屏幕外无必要的绘制与高频表现更新，保留必要玩法推进。
3. 预加载常用资源，复用弹壳、火星、爆炸等高频对象。
4. 控制大面积透明烟雾、光晕及重复混合，合并同图集绘制。
5. 降低远景装饰动画频率和无关粒子密度。
6. 如仍不足，增加低特效档，并重复完整压力与可读性检查。

每次优化要有前后同场景数据，性能变好不能以漏画敌人、丢输入或改变战斗规则为代价。

## 10. 风险与应对

| 风险 | 应对 | 影响 |
| --- | --- | --- |
| AI 辅助图集角色比例或细节不一致 | 统一锚点、逐帧校对，必要时重制或修绘；保留版本与来源 | M1 可能返工，不以强制拉伸掩盖问题 |

| 背景太亮、太密或重复明显 | 重做独立层，降低玩法层后方对比，修复拼接 | 以实际手机可读性判断 |
| 透明特效造成发热与掉帧 | 限制覆盖面积、池化、装饰降级，实测对比 | 必要时降低特效密度 |
| 重构引入行为回归 | 小步拆分、保留固定步长测试与可复现状态 | 不与大量玩法调整同时进行 |
| 多设备或手柄不可用 | 先完成当前设备，明确标记未测试并列出所需条件 | 不阻止阶段 APK，阻止相应最终验收结论 |
| 正式签名条件未提供 | 调试包继续交付，正式发布另行安排 | 不生成或索取聊天中的明文私钥 |
| 缺少可用版本管理 | 建立本地可恢复源码快照与清单；可用时再接入版本控制 | 不宣称已提交 Git 或已有远端备份 |
